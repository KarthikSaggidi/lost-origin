# Receipts, email and WhatsApp

Online orders and court bookings collect an email address, show a closable
confirmation dialog, and offer a PDF download. The PDFs use recorded item prices,
tax and totals. They do not imply that a payment gateway collected money.
Completing a court game also queues its final bill by email.

Email delivery is intentionally deferred until SMTP is configured. The UI shows
pending delivery honestly. An email failure never reverses a successful order or
booking. Notifications are inserted atomically with the business transaction and
have stable IDs, so submitting the same transaction again does not send another
confirmation. Guests can download their receipt with its private request key;
signed-in customers can access their own records; administrators can access all.

## Node service

The Sites Worker delegates SMTP and WhatsApp Web to a persistent Node service in
`services/communications`. It runs separately from the website (5173) and admin
(5174), on **5175** by default. It uses Nodemailer, whatsapp-web.js with LocalAuth,
and a durable SQLite delivery queue. Only the application server can call it:
requests have a keyed SHA-256 signature covering the method, path, timestamp and
body. Browser-origin requests are rejected. No service keys reach the frontend.

Local setup:

```sh
cd services/communications
PUPPETEER_SKIP_DOWNLOAD=true npm ci --omit=optional
cd ../..
npm run communications:setup
npm run dev:all
```

The setup command generates matching server keys in ignored, mode-0600 local
environment files. It does not configure SMTP. On macOS it uses the installed
Chrome. Elsewhere set `CHROME_EXECUTABLE_PATH` to the installed Chrome/Chromium.
Run Chrome as a non-root service user with its sandbox enabled. The browser
runtime is pinned to a patched version. Unused RemoteAuth archive dependencies
are omitted; LocalAuth is the supported session strategy for this deployment.

For hosted delivery, deploy the Node service on a persistent Node 22.13+ host
with Chrome and a private persistent volume for `.auth` and `.data`. Expose it
over HTTPS and set the backend's encrypted `COMMUNICATIONS_SECRET` and
`COMMUNICATIONS_URL` runtime variables. Set the matching key in the Node service.
Keep its origin private to the backend where the hosting network permits. A
hosted Worker cannot call a laptop's loopback address.

The gateway API is not an application route and must not be made into a public
browser endpoint or given permissive CORS. Its health/status and QR endpoints
also require server authentication. The application's admin API requires the
separate admin session, exact Origin and CSRF token.

## SMTP configuration (later)

Set `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, and
`SMTP_FROM` in the Node service's secure environment. Use port 465 with
`SMTP_SECURE=true`, or the provider's STARTTLS port with `SMTP_SECURE=false`.
STARTTLS is required for the latter. Certificate checks remain enabled.
Credentials are never entered in client settings or committed to source.
Restart after changing SMTP variables; waiting jobs resume automatically.

Messages include the confirmation details and a real PDF attachment. Nodemailer
cannot fetch attachment files or URLs: only server-created in-memory bytes are
accepted. Email addresses and subject lines are validated against header
injection. Public transaction requests are rate limited before creating mail.

## WhatsApp and messages

In Admin → WhatsApp, click **Connect WhatsApp**, then scan the displayed QR using
WhatsApp → Linked devices → Link a device. The QR is generated by WhatsApp Web,
expires, and refreshes. The linked session remains on the Node host. Disconnect
logs out the linked device. QR connection is not the official Business Cloud API;
an account owner must complete linking before any WhatsApp delivery can be tested.

Each saved bill has a **Share bill on WhatsApp** action with a PDF attachment and
an editable thank-you message. Order details also have **Send WhatsApp update**.
The defaults are editable on the WhatsApp page and support `{name}`, `{reference}`,
`{total}`, `{status}`, `{date}`, `{time}` and `{court}`. Sending requires an
explicit admin action. Editing a template alone does not send messages.

Campaigns and the WhatsApp page have contact search, individual selection,
**Select all eligible contacts**, a custom message and optional uploaded image.
Contacts are deduplicated by phone. Only recorded WhatsApp campaign opt-ins are
eligible; existing contacts default to no consent. Orders, bookings and popup
registrations expose an optional opt-in checkbox. Batches are limited to 100 and
WhatsApp delivery is paced by the gateway queue.

Delivery states distinguish Pending, Waiting for SMTP/WhatsApp, Queued, Sending,
Sent, Failed and Unknown. Sent means accepted by SMTP or WhatsApp, not that a
customer opened the message. Known failures can be retried. Unknown deliveries
are not automatically resent: review the provider to avoid duplicate bills.
Pending records can be submitted after service setup using **Process pending
messages**. Keep both databases and WhatsApp session data backed up privately.

## Verification

`npm test` includes PDF content, pagination and template tests.
`npm --prefix services/communications test` covers signed-request tampering and
Nodemailer's actual MIME attachment generation without sending external email.
Financial integration tests use only local services and test contacts.
